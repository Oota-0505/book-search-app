# このプロジェクトで学んだこと

書籍横断検索アプリ「Book Finder」の開発・調査を通じて学んだことのまとめ。
（適法性調査の詳細は [`scraping_monetization_report.md`](scraping_monetization_report.md) を参照）

---

## 1. 「技術的に作れる」と「やってよい」は別物

このプロジェクト最大の学び。スクレイピングは requests と BeautifulSoup があれば誰でも書けるが、
それを動かしてよいかは別の問題として検証が必要だった。

- **robots.txt は法律ではないが、無視してよいものでもない**。
  法的拘束力はない一方、トラブルになったとき「禁止を知りながら続けた」事実は
  民事・刑事のどちらでも決定的に不利に働く。
- 実際に調査した結果、対象4サイトのうち可児市立図書館の robots.txt が
  検索パス `/csp` への自動アクセスを禁止しており、2026年5月には運営側が
  「サーバ負荷軽減」の注記まで追加していたことを確認した。
- これを受けて、**同館へのスクレイピング機能を撤去し、検索リンクの提示のみに設計変更**した。
  機能を削る判断だったが、明示された意思表示を尊重する方が長期的に正しいと考えた。

## 2. 図書館OPACへの自動アクセスには「前例」がある

**岡崎市立中央図書館事件（Librahack事件、2010年）**を調べたことで、リスクの解像度が大きく上がった。

- 利用者が新着図書ページを約1秒に1回という常識的な頻度でクロールしただけで、
  図書館システム側の欠陥によるサイト障害の責任を疑われ、偽計業務妨害容疑で逮捕された
  （20日間勾留、起訴猶予）。
- 教訓: **自分のアクセスが軽くても、相手のシステムが脆弱なら疑われるのは自動アクセスしていた側**。
  だからこそ robots.txt の遵守・キャッシュによる負荷抑制・User-Agent の明示といった
  「誠実に運用していた証拠」を残すことに意味がある。

## 3. 個人利用と公開サービスは、リスクがまったく別物

- 自分ひとりが手動検索の代わりに使う分には、負荷はブラウザでの閲覧と同等で実害はほぼない。
- しかし公開すると、**不特定多数のユーザーのアクセスを自分が肩代わりして相手サーバーに流す**
  ことになり、負荷・規約・責任のすべてが桁違いになる。
- 「個人でグレー」は「公開でもグレー」を意味しない。この非対称性を理解して、
  本アプリは**個人利用＋コード公開のみ**（デプロイなし）と線を引いた。

## 4. 収益化は「できない」かつ「割に合わない」— 調査して、やらないと決めた

収益化も含めて調査した上で、以下の理由から**やらない**と判断した。

**法的に「できない」側の理由:**
- TSUTAYA（T-SITE）の利用規約は第9条(7)で「営利を目的とする行為」を明示的に禁止。
  第8条で私的使用を超えた情報利用も禁止しており、商用化は正面から規約違反になる。
- 岐阜市立図書館のサイトポリシーも私的利用の範囲の複製しか認めておらず、商用は許諾が必要。
- つまり現在の構成のままの収益化は選択肢として存在しない。

**経済的に「割に合わない」側の理由:**
- 合法化ルートは存在する（図書館→カーリル図書館API［無償・商用可］、書店→リンクアウト化、
  収益→楽天アフィリエイト＋Amazonアソシエイト）。
- しかし収益モデルは「検索数 × クリック率 × 購入率 × 単価 × 料率2〜4%」で、
  地域特化アプリのトラフィックでは**月数百円〜数千円**が現実的な上限と試算した。
- さらに「全国の図書館横断検索」はカーリルという完成度の高い先行サービスが無料で存在し、
  単純な蔵書検索では勝ち目がない。
- 大規模な改修コスト＋規約リスクと、月数千円の期待収益は釣り合わない。
  **「調査した結果、やらない」も立派な意思決定**であり、調査の過程と根拠を
  レポートとして残したこと自体がこのプロジェクトの成果だと考えている。

## 5. 技術面の学び

- **Streamlit の session_state の罠**: ウィジェット生成後に同じキーの
  `st.session_state` を書き換えると `StreamlitAPIException` が発生する。
  「次回 run の生成前に反映する」pending パターンで解決した。
- **キャッシュは UX とマナーの両方に効く**: `st.cache_data(ttl=600)` を入れることで、
  履歴ボタン連打やリロード時に相手サーバーへ再アクセスしなくなり、
  応答も即時になった。外部サイトに依存するアプリではキャッシュ設計が誠実さの一部になる。
- **並列化の効果と責任**: ThreadPoolExecutor による4サイト同時リクエストで体感速度は
  大幅に改善するが、同時アクセスは相手側から見れば瞬間的な負荷でもある。
  並列化とキャッシュ・頻度制限はセットで考えるべき。
- **スクレイピングは構造変化に弱い**: 在庫判定がHTML内の文言（「在庫あり」「○ 在架あり」等）に
  依存しており、サイト改修で静かに壊れる。公式APIがあるなら常にそちらが正しい選択。

## 6. 最終的な意思決定のまとめ

| 論点 | 決定 | 理由 |
|---|---|---|
| ミライブのスクレイピング | 撤去（リンク提示のみ） | robots.txt の明示的な禁止＋運営の負荷軽減表明 |
| 他3サイトの在庫チェック | 個人利用の範囲で継続 | robots.txt 準拠 or 禁止の意思表示なし＋負荷は閲覧同等 |
| アプリの公開（デプロイ） | しない | 公開すると規約・負荷・責任の前提が変わるため |
| コードの公開 | する（GitHub） | 合法であり、適法性検証まで含めてポートフォリオとして提示 |
| 収益化 | しない | 規約上不可＋合法化しても費用対効果が合わない（調査済み） |
