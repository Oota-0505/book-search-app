# Streamlit → FastAPI 移行レポート

- 実施: 2026-09-05
- 動機: **スマホから開くと起動が遅い**

---

## 1. 計測（移行前）

体感ではなく実測から始めた。ローカル（同一マシン・キャッシュ温）での数値。

| 区間 | 時間 |
|---|---|
| `streamlit run` → HTTP応答 | 1.65 秒 |
| ページを開いて内容が見えるまで | 4.83 秒 |
| **合計** | **約 6.5 秒** |

内訳を分解すると、原因は2つに分かれた。

### 原因A: フレームワーク由来（約3秒） — Streamlit を使う限り消せない

- 何を表示するにも **1.75MB の JavaScript バンドル**の取得と実行が先に必要
- そのうえで WebSocket を張り、サーバーから描画命令を受けて初めて画面が出る
- 初回のページ転送量は **1.95MB**

### 原因B: アプリ側のコード（約1.8秒） — 直せる

実測で見つかった具体的な不具合。

1. **CSSがキャッシュされていなかった**
   `_build_app_css()` は「（キャッシュ済み）」とコメントされていたが、
   **`@st.cache_data` が付いていなかった**。毎回 CSS 6ファイルをディスクから読み直していた。

2. **背景画像を毎回 base64 で送っていた**
   背景 JPEG（164KB）を base64 化して CSS に埋め込む実装。
   実測で**インラインCSSが 232KB**あり、DOM全体 255KB の 93% を占めていた。
   これがボタンを押すたび、履歴を開くたびに WebSocket を流れていた。

3. **検索結果で 6.2MB の base64 を流し込んでいた**
   カード背景4枚をすべて data URI で HTML に埋め込んでいた。
   とくに `岐阜駅本屋.png` は **3.7MB**（base64 で 5.0MB）。

4. **画像がブラウザにキャッシュされない**
   data URI は動的に生成される HTML の中にあるため、
   何度開いても毎回まるごと転送されていた。

---

## 2. 判断

原因Bを直しても**約3秒の下限は残る**。
主な用途がスマホであることを踏まえ、フレームワークごと乗り換えることにした。

FastAPI + Jinja2 の1ページ構成なら:

- 最初の HTML がそのまま画面になる（JSバンドルの待ち時間がゼロ）
- 画像・CSS・JS が**普通の静的ファイル**になり、ブラウザにキャッシュされる
- PWA化が素直にできる（Streamlit だと内部にパッチを当てる必要があった）
- スクレイピングのロジックはそのまま流用できる

## 4. リファクタリングの内容

907行の `app.py` 1ファイルを、責務ごとに分割した。

| ファイル | 責務 |
|---|---|
| `main.py` | ルーティングのみ |
| `config.py` | 定数・パス（**すべてファイル位置基準**に修正） |
| `models.py` | `BookStatus` / `SiteResult` |
| `providers.py` | 各サイトの在庫チェック（**唯一、外部へ通信する層**） |
| `search.py` | 並列検索 + TTLキャッシュ |
| `history.py` | 検索履歴の永続化 |
| `logging_config.py` | ロギング |

### あわせて直した不具合

- **ログの保存先がカレントディレクトリ依存だった**
  `Path("logs")` を使っていたため、起動する場所によって出力先が変わっていた。
  ファイル位置基準に変更。
- **`Dict[str, object]` という型で結果を持ち回っていた**
  `tsutaya` だけタプル、他は `BookStatus` という不揃いな構造だったため、
  `SiteResult` に統一。サイトの追加も1行で済むようになった。
- **1サイトが想定外の例外で落ちるとリンクも失われていた**
  各サイトに「リクエストを送らないURLビルダー」を必ず持たせ、
  例外時でもカードのリンクは生きるようにした。
- **Amazonボタンの実装が総当たりだった**
  Streamlit では JS が除去されるため、`components.html` の iframe から
  親ドキュメントの `input` を総当たりで探して値を取っていた。
  素のHTMLになったので、入力欄を直接読むだけになった。
- **CSSの重複を解消**
  `a.btn-amazon` のスタイルが `cards.css` と iframe 内の両方にあり、
  前者は iframe 化以降どこにも効いていなかった。
- **`!important` の大半を削除**
  Streamlit のスタイルを打ち消すためだけに付いていたもの。
- **背景の指定方法を iOS 対応に変更**
  `background-attachment: fixed` は iOS Safari で描画が崩れる既知の不具合があるため、
  `position: fixed` の擬似要素に変更した。

## 5. 検証

### 自動テスト（22件）

```bash
.venv/bin/python -m pytest tests/ -q     # 22 passed
```

- ルーティング・Content-Type・`Service-Worker-Allowed` ヘッダ
- 空/長すぎるキーワードの拒否
- **同一キーワードの再検索で外部サイトへ再アクセスしないこと**
- **全滅した結果をキャッシュに残さないこと**（復旧後すぐ再試行できるように）
- 1サイトが例外で落ちても他が巻き込まれないこと
- PWA: manifest の必須項目、アイコンの実サイズ、**四隅の不透明性**、
  SWのキャッシュ方針（GET以外・別ドメイン・API を触らないこと）

### 実ブラウザ検証（PWA_GUIDE §10-2）

`tools/verify_pwa.py` で実 Chrome を CDP 経由で操作して確認。**全10項目合格**。

```
✅ secure context          ✅ SW が登録されている      ✅ SW が activated
✅ スコープがルート         ✅ manifest が読める        ✅ アイコンが4種
✅ キャッシュが作られている  ✅ GET以外を入れていない
✅ HTMLはoffline.htmlのみ   ✅ APIを入れていない
```

### オフライン動作（§10-4 相当）

**uvicorn を実際に停止**したうえで画面遷移し、`offline.html` が表示されることを確認した。

```
サーバー停止済み。到達不可を確認: 000
オフライン時の画面: {"title":"オフライン — Book Finder","h1":"オフラインです"}
```

> なお、ブラウザのプレビュー枠では Service Worker がそもそも登録できず
> （1行のSWを素の `http.server` で配っても同じエラーになることをA/Bテストで確認）、
> 実ブラウザでの検証が必須だった。
